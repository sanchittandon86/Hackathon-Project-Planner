PRIORITY 1 — CAN CAUSE REAL DATA LOSS  [FIXED 2026-09-26]
-----------------------------------------------------------------------------
2. Plan generation can wipe ALL plans if the save step fails  [FIXED]
   File    : lib/planningEngine.ts -> savePlanToDB()
   Problem : The save flow was: (1) insert version history, (2) DELETE all
             existing plans, (3) INSERT the newly generated plans. There
             was no database transaction wrapping these steps. If step 3
             failed for any reason (bad row, network blip, transient
             Supabase error), the function just returned false — but step 2
             had already run. Every plan row was gone with nothing to
             replace it.
   Fix applied : Reordered to insert-new-plans-first, then delete only the
             specific old rows being replaced (captured by id up front).
             If the insert fails, the function now returns false with the
             old plans completely untouched — no data loss window anymore.

3. Unchecking "Exclude Completed" during Generate Plan destroys history  [FIXED]
   File    : lib/planningEngine.ts -> savePlanToDB()
   Problem : If a user unchecked "exclude completed" and clicked Generate
             Plan, the old code deleted ALL plans (including completed
             ones) and reinserted fresh plans with is_completed = false by
             default — permanently erasing completion history
             (is_completed, completion_type, completed_at) for tasks that
             were already marked done.
   Fix applied : savePlanToDB() now always protects completed plans at the
             persistence layer, regardless of what the excludeCompleted
             flag says. Any incoming generated plan for a task that already
             has a completed plan on file is dropped before insert, and
             completed rows are never included in the delete step. The
             checkbox in the UI can no longer cause this.

2b. [NEWLY DISCOVERED WHILE FIXING #2/#3] plan_versions rows were being
    silently destroyed by a cascade-delete on every regeneration  [FIXED]
   File    : schema.sql / migration_fix_plan_versions_history.sql
   Problem : plan_versions.plan_id referenced plans(id) with "ON DELETE
             CASCADE". Every "Generate Plan" click deleted the old plan row
             right after recording a version for it — which cascaded and
             deleted the just-created version record too. Version History
             would only ever show the leftovers of whatever partially
             survived, never a real history.
   Fix applied : Ran a migration against the live Supabase DB changing
             plan_id to be nullable with "ON DELETE SET NULL" instead of
             CASCADE. Verified live: generated a plan twice in a row and
             confirmed version records from the first generation survive
             the second regeneration's delete step.

2c. [NEWLY DISCOVERED — BIGGER THAN #2/#3 — bigger than everything else in
    this file] Row Level Security is enabled on every table, but several
    required policies were simply missing, so multiple features were
    silently no-ops against the real database  [FIXED]
   File    : migration_fix_missing_rls_policies.sql
   Problem : Confirmed directly against the live DB (via raw REST calls
             with the app's own anon key) that, before this fix:
               - leaves table: SELECT/INSERT/UPDATE/DELETE ALL blocked.
                 The Leave Management page always showed 0 leaves and
                 "Add Leave" silently failed, no matter what you entered.
               - plan_versions table: SELECT/INSERT/UPDATE/DELETE ALL
                 blocked (separate from bug 2b above — even after fixing
                 the cascade issue, the insert itself was rejected).
                 Version History was empty because it could never write a
                 row in the first place.
               - plans table: UPDATE and DELETE blocked. "Mark Complete"
                 on a plan silently did nothing. Every "Generate Plan"
                 click's delete step silently deleted 0 rows (no error!),
                 so old plans just piled up forever — confirmed live: the
                 plans table had grown to 13 duplicate rows before this fix
                 from repeated regenerations that never actually cleaned
                 up.
               - tasks table: UPDATE and DELETE blocked. Editing or
                 deleting a task from the UI silently did nothing.
               - employees table: DELETE blocked. Deleting an employee
                 silently did nothing.
             None of this throws a visible error in most cases (Postgres
             RLS just makes DELETE/UPDATE match 0 rows) — the app logs
             "success" every time, which is why this went unnoticed.
   Fix applied : Ran a migration adding the missing SELECT/INSERT/UPDATE/
             DELETE policies (matching the same fully-open anon+
             authenticated pattern already used on the tables that did
             work). Verified live: leaves can now be added and read, plan
             completion updates persist, tasks/employees can be edited and
             deleted, and "Generate Plan" now actually replaces old plans
             instead of accumulating duplicates (confirmed count dropped
             from 12 to 3 after one regeneration).
   Note    : This app still has no authentication (see item #4 below) — an
             anon key with full CRUD is only appropriate for a private/
             internal tool, not a public deployment. This fix restores the
             functionality the app's own code already assumed existed; it
             does not address that broader gap.


PRIORITY 2 — SECURITY  [FIXED 2026-09-27]
-------------------------------------------------------------------
4. No authentication at all  [FIXED]
   Problem : lib/supabase/server.ts and lib/supabaseClient.ts both used the
             public anon key with no login/session system. No /login page,
             no middleware.ts. Anyone with the anon key (public in the
             client bundle by design) had full read/write access to every
             table via the Supabase REST API directly.
   Fix applied : Chose "simple shared login" (matches the existing
             single-tenant data model - no per-user ownership, everyone who
             logs in sees the same shared data):
               - Migrated lib/supabase/server.ts and added lib/supabase/
                 client.ts to use @supabase/ssr (cookie-based sessions)
                 instead of a plain stateless anon-key client. Removed the
                 deprecated unused @supabase/auth-helpers-nextjs dependency
                 (also closes old item #7) in favor of @supabase/ssr.
               - Added middleware.ts + lib/supabase/middleware.ts:
                 redirects any unauthenticated request to /login (preserving
                 the originally-requested path to return to after login).
               - Added app/login/ (page + LoginForm + server actions for
                 login/logout), no signup page - accounts are provisioned
                 directly in the Supabase Dashboard.
               - Added a "Log out" button to the sidebar.
               - Deleted app/api/complete-plan/route.ts and app/api/
                 plan-versions/route.ts: both were dead code (confirmed via
                 grep - nothing calls them), both used the old stateless
                 anon client, and both would have silently broken once RLS
                 was restricted below. Also closes old item #6.
               - Ran migration_restrict_rls_to_authenticated.sql against the
                 live DB, changing all 22 RLS policies from
                 "anon, authenticated" down to "authenticated" only. This is
                 the step that makes the login screen actually enforce
                 access control rather than being cosmetic.
   Verified live : Logged in through the real browser with a Supabase Auth
             account, confirmed all pages load real data through the
             authenticated session. Then confirmed the raw anon key can no
             longer read anything at all (tested tasks + employees directly
             against the Supabase REST API - both now return empty/blocked).
             Unauthenticated requests to any app route correctly redirect
             to /login.

5. No error boundaries or 404/loading pages  [FIXED]
   Problem : No app/error.tsx, no app/not-found.tsx anywhere in the app/
             folder. An unhandled exception showed the raw Next.js crash
             screen instead of a graceful message.
   Fix applied : Added app/not-found.tsx, app/error.tsx, and
             app/global-error.tsx (covers errors thrown from the root
             layout itself, which app/error.tsx can't catch), styled to
             match the existing shadcn/Tailwind design system. Verified
             live: hitting an unknown route now returns a proper 404 page
             instead of Next's default screen; existing routes unaffected.
